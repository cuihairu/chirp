# Game chat features

Last updated: 2026-10-15 (emoji/sticker landing notes; the P1 skill link card landed — reconciled against the source of truth, with measured landing dates and divergence rulings noted)

This document lists the features a game chat system needs to support, staged by priority.

## P0 — Core (required for game launch)

### Message handling

- **Sensitive-word filtering** (landed 2026-09-22, server + client in both forms): the server send chain `WordFilter::Filter` has a two-level policy — Replace (substitution, consecutive hits collapse) / Reject (block); the word list hot-reloads and pushes every 5 seconds (after login, via `HandleWordFilterFetch`, conditional GET + guard), and a load failure is fail-open without blocking sends; only the send side is filtered. The client pre-check is the same `WordFilterInterceptor` in three languages (C++/C#/TS, sharing the same word-list file with the server). **Divergence from this document**: the original three levels (replace/reject/record for review) landed as two — Record (audit) is a server-side governance duty and does not enter the client filter chain.
- **Message length limits** (landed): `ValidateContentLength` applies per-channel caps via `MaxContentChars` — private 200 / world 100 / system announcement 500 code points, with no cap on the TEAM/GUILD/MARQUEE coordination surfaces; counting is by Unicode code point (not UTF-8 bytes), and over-length returns `CONTENT_TOO_LONG` (no truncation); mounted in `ValidateSendMessageRequest` (same chain in both the basic/enhanced forms).
- **Send rate limiting** (landed 2026-09-14): a 60s fixed window per user (Redis counter, `ChatRateLimiter::CheckSend`; login additionally has a per-IP fuzzy limiter via `CheckLogin`) + per-channel pacing (world 5s / guild 2s / private 1s, ChannelPacer), returning `RATE_LIMITED` when over.
- **Duplicate message detection** (landed 2026-09-22): `RepeatGuard` — 3 identical consecutive messages from the same user triggers an automatic 5-minute mute (`kRepeatTriggerCount=3` / `kRepeatMuteMs=5min`), positioned in the send chain after pacing and before the word filter; sends during the mute window return `MUTED`.
- **Message recall** (landed: `MessageEditManager::RecallMessage`, window `--recall_window_sec` defaulting to 120s, recallable channels `--recall_channels` defaulting to `private,guild`; moderator deletes go through the `DeleteMessage` governance path and are not bound by the window. Return codes: non-sender `AUTH_FAILED`, out-of-window / non-recall channel / duplicate recall `INVALID_PARAM`, no ledger in this process `USER_NOT_FOUND`): messages can be recalled within 2 minutes of sending (private/guild). After recall the other party's bubble is replaced with a "message was recalled" tombstone via `MESSAGE_DELETED_NOTIFY` (`is_hard_delete=false`, `deleted_by=author`), and copies already queued in the recipient's offline queue are reclaimed by `message_id`. **The history-archive tombstone is fully wired (2026-09-27)**: the tombstone semantics are "set `is_recalled` + wipe the body" — setting the flag alone would leave the original text sitting in the archive — so both `MessageStore::MarkMessageRecalled` and the basic form's `MarkRecalled` also clear `content` (MySQL `UPDATE ... SET is_recalled = 1, content = ''`; Hybrid dual-tier: the Redis hot tier rewrites in place with `LSet`, leaving list order and other entries untouched, and the cold tier runs the same UPDATE; the mirror is the `ChatMessage` proto bytes, and the wipe logic is consolidated into `recall_tombstone.{h,cc}` shared by the three storage implementations). So re-fetching `GET_HISTORY` yields only the fact that "this was recalled", never the original text; `BULK_DELETE` soft delete carries the same semantics as single soft delete (tombstone per successful item, copy reclaimed per member). **Both deployment forms have the recall entry point (2026-09-27)**: besides basic, the enhanced form (the `main_enhanced.cc` actually built when `MYSQL_FOUND`) previously had no `DELETE_MESSAGE` slot at all, and is now wired to the same `MessageEditManager`/`MessageEditHandlers` — the send side records the ledger, and the recall side fans the tombstone out to every online device of the recipient via the session registry, with the marker/purger wired to `HybridMessageStore::MarkMessageRecalled` (dual-tier wipe) and `PurgeOfflineByMessageId` (scanning both Redis and the Redis-down fallback queue). Two recorded form divergences: the game plane has no group subscription ledger, so member resolution covers private chat only (the canonical `a|b` key takes the other party), making guild recall's notify/offline reclaim a no-op against an empty member list — the same gap as channel muting, to land together with the group fan-out path; and with no role system the moderator check is always false (fail-closed), so `is_hard_delete=true` is always `AUTH_FAILED`. Zero gateway changes: authenticated connections forward 2001-2999 verbatim, and `MESSAGE_DELETED_NOTIFY` (2232) reaches the client through the ServiceBridge's verbatim pipe.
- **@mentions** (landed 2026-09-21): `MentionManager`/`MentionHandlers` — the send side's `ProcessOutgoingMessage` extracts mentions and delivers them with the message (`ChatMessage.mentions` / `mentioned_user_ids` / `mentions_everyone` / `mentions_here`, rendered as highlights by the receiver per field); group member suggestions via `GetMentionSuggestions` (`@someone` completion).

### Channel management

- **World channel** (landed): server-wide broadcast; the speech level gate is in the P1 chat level threshold row (`LEVEL_REQUIRED = 13`, `--world_channel_min_level` default 0 = off); pacing of one message per 5 seconds.
- **Guild channel** (landed): group members auto-join and are auto-removed on leave/kick (`GroupManager` in-memory ledger, same lifecycle as the group itself); guild managers can set speech permissions (MODERATOR+, see the P1 mute row).
- **Party channel** (landed): auto-created on party formation, auto-destroyed on disband/leave (party service); only the leader can disband.
- **Private chat** (landed): 1v1 conversation; offline messages are queued (cap 200) and pushed for redelivery at login (the enhanced form has both the offline-queue and history-rebuild arms).
- **System announcement channel** (landed): server-wide read-only broadcast, delivered via the game plane's inject (the chat service treats it as a read-only broadcast and produces no player speech path); announcement bodies are capped at 500 code points.
- **Channel muting** (landed 2026-09-23): `DeliveryPrefs.SetChannelMuted` / `GetChannelMutes` — the world/guild/party channels can be muted (push filtering: history stays browsable, and offline messages queued before the mute are still redelivered at login); MARQUEE / SYSTEM_CHANNEL service broadcasts cannot be muted (the `kMuteableChannels` allowlist); "don't hear this person's messages" belongs to the blocklist dimension (next row).

### Message display

- **Marquee** (landed 2026-10-14, companion form): messages with `priority = URGENT` + `ttl_seconds > 0` scroll across the top of the screen. Only one shows at a time; a new one replaces the old. The decision function lives in the companion api layer (`systemSurfaceOf` in `chat_api.ts`, same logic in web/desktop): `PRIORITY_HIGH` is checked first (goes to the popup), and `PRIORITY_URGENT` with `ttl > 0` goes to the marquee; events are dispatched through the `ChatApi.onSystemSurface` single slot — a new one replaces the current slot without stacking, regardless of notification permission or the currently open conversation/channel. Web `MarqueeStrip` (a top bar that auto-hides on expiry and resets the timer on content change), desktop `MarqueeStrip` (same, in the window top bar). **Scope ruling**: scroll animation, duration and replacement semantics are as this document describes; the in-game client's own rendering (real scroll speed and click-to-jump) goes through the SDK side, and the companion surface only displays.
- **System popup** (landed 2026-10-14, companion form): system messages with `priority = HIGH` pop up (maintenance notices, server-wide rewards). Web/desktop `SystemAnnounceDialog` (closes on confirm, multi-line body preserves line breaks); the message itself still stays in the conversation stream as a normal bubble and does not disappear because of the popup.
- **Message bubbles** (landed 2026-10-14, companion form): styles differ by `sender_kind` — ordinary players paper-colored, system yellow, NPC green, trade orange. The web `MessageBubble` and the desktop `ChatPanel` MessageRow share the same mapping (`KIND_FACE` table + `data-sender-kind` tag for test assertions); your own messages always use the primary color (a client can structurally only send as a player, so this is settled by `mine` rather than by kind); unknown values outside the enum fall back to the player face color (forward-compatible, no undefined base color left behind). The three fields `ChatMessage.priority / ttl_seconds / sender_kind` pass through web/desktop `toView`, with history and live paths sharing the same handling.
- **Item links** (landed 2026-10-14, companion form): `msg_type = ITEM_LINK`, clickable for a detail popup. Quality colors: white (common) / green (fine) / blue (rare) / purple (epic) / orange (legendary) (integer codes 0-4; unknown values outside the enum fall back to white rendering). The server validates metadata at the send gate — unparseable `ItemMetadata` or a missing `item_id` returns INVALID_PARAM (same handling in both basic/enhanced forms, metadata of non-ITEM_LINK messages passes through verbatim); web `MessageBubble` and desktop `ChatPanel` render the item card (name colored by quality, ×N shown when count>1, item_id caption), and clicking opens the detail popup (itemId/iconUrl/count/attrs key-value list, `data-quality` tag for test assertions). The in-game client's own item detail rendering goes through the SDK side (same batch shape as coordinate links: `ItemMetadata` rides the generic ChatMessage.metadata pipeline, zero SDK changes across the four ends).
- **Message history** (landed): messages from while offline are pulled at login, `GetHistoryRequest` paginated loading (`limit` + `before_timestamp` cursor + `has_more`); the enhanced form rebuilds via both the history and offline-queue arms (metadata fidelity along the whole chain).
- **Message read state** (landed): `unread_ledger` unread badges (`MarkRead` / `GetUnreadSummary`, shared via game_server_gateway 5035-5036 with the multi-device online device surface); read receipts `StoreReadReceipt` / `GetReadReceipts` (MySQL cold-tier trace by message_id); private-chat bubbles render a "read" marker against the peer's read cursor.

### User behavior

- **Blocklist** (landed 2026-09-23): `DeliveryPrefs.BlockUser` / `UnblockUser` / `IsUserBlocked` — after blocking, the other party's private messages are silently dropped (the sender sees success, nothing is enqueued offline), and channel messages are filtered per member and not delivered; unblocking is idempotent (unblocking someone never blocked still reports success); `GetBlockedUsers` lists them. **Divergence from this document**: channel messages from a blocked party are simply not delivered (the recipient is unaware), with no "message from a blocked user" placeholder rendering.
- **Presence** (landed): `services/social` `PresenceManager` is server-authoritative (online/busy/away/invisible), visible to friends; social RPCs 3001-3029 (friend roster + the online-notification toggle in the P1 friend-online row).
- **Typing** (landed): `TypingIndicator` channel broadcast (proto 899-902), the receiving end aggregates per conversation and shows "the other party is typing…" (web/desktop typing store with local TTL state).

## P1 — Enhanced (post-launch iteration)

### Message handling

- **Message editing** (landed 2026-09-18): `EDIT_MESSAGE_REQ/RESP = 2225/2226` (gateway.proto:116). Server-side `MessageEditHandlers` + `MessageEditManager` in-memory ledger (edit count cap `max_edit_count=100`, edit history capacity `max_edit_history_size`, rejects over the cap; `is_edited`/`edit_count`/`edit_history` delivered with ChatMessageFull). All four SDK ends aligned (C++ core `ChatClient::EditMessage`, the sdks/ts and apps/shared/protocol dual packages' msg_map spec, C# in the same batch); web/desktop `editMessage` (chat_api.ts:540 mirrored on both ends) + the bubble "edited" marker. **Divergence from this document**: the original text said "editable once, edit history not kept" — in reality up to 100 edits (configurable), with the edit history kept and delivered with the message.
- **Emoji/stickers** (landed 2026-10-15, companion form): 16 built-in system emoji (web_companion `components/emoji.ts` and desktop `ui/emoji.ts` are identical `SYSTEM_EMOJIS`). `[emoji:code]` in message text is expanded by `expandEmojiCodes` into slices rendered as emoji characters (regex `[a-z0-9_]+`, unknown codes kept verbatim as literals — forward-compatible, same fallback posture as sender_kind/quality/rarity); the input surface carries an emoji picker (emoji button + Popover grid, clicking inserts `[emoji:code]` into the draft). **Zero server changes**: emoji travels as TEXT content passthrough, with the length/word-filter gates applying as usual; zero SDK changes across the four ends (the metadata pipeline is not involved). Stickers (large image packs) are not done — awaiting sticker assets and a metadata carrier (following the ACHIEVEMENT batch shape) in a separate batch.
- **Message quoting** (landed 2026-10-11): `replyToMessageId` passes through the whole SEND_MESSAGE chain (4th parameter on send + wire field + history read-back mapping, web chat_api.ts:307/348/400/1039, desktop mirrored); the bubble renders a quoted summary block (the `MessageBubble` quoted area, same shape on web/desktop; when the quoted message is deleted or not visible, a "original message deleted or unavailable" placeholder shows). The server passes it through as an ordinary field (no separate validation gate).
- **Rich text** (landed 2026-10-15, companion form): `**bold**` and `*italic*` markers in message text render as strong/em inside the bubble — web `MessageBubble` and desktop `ChatPanel` share the shape (`parseRichText` identical on both ends: web `components/rich_text.ts`, desktop `ui/rich_text.ts`, 10 unit tests each). **Zero server changes**: markers travel as TEXT content passthrough, with the length/word-filter gates applying as usual (same posture as the P1 emoji batch). **Deliberately conservative parsing**: the character left of a delimiter must not be whitespace (start-of-string counts as a legal boundary), and the span must be non-empty and pair-closed, otherwise the literal is kept verbatim — bare asterisks/underscores like "2 * 3 = 4" or "user_id" are not swallowed, and an unclosed `**bold**`-prefix also displays as-is (no whitespace constraint is added on the right-delimiter side, since markers glued to the preceding character are more common in Chinese text). **Divergence from this document**: colors (VIP privilege) are not done — the chat surface has no VIP entitlement data source (the same gap as the chat level threshold), to land together with the entitlement surface once it exists; `message_interceptor.h` already leaves a VIP effect seam but has no entitlement input.
- **Skill links** (landed 2026-10-15, companion form): `msg_type = SKILL_LINK` (a proto type that long predates this batch, whose consumption chain is now filled in), card-style display (icon + name + `Lv.N` + description + skill_id caption). Payload rides `SkillMetadata{skill_id, skill_name, level, icon_url, description}` (the generic metadata pipeline, zero SDK changes across the four ends); the server send gate validates — unparseable or missing `skill_id` returns INVALID_PARAM (same layer and posture as coordinate/item/achievement/trade/recruit, wired in both basic/enhanced forms); web `MessageBubble` and desktop `ChatPanel` render the skill card (level=0 hides the level surface, a missing name falls back to skill_id). **Scope ruling**: the rendering matrix's original "clickable skill card" lands as a display card (same ruling as achievement sharing: the details are the card body, no expandable second-level data surface); in-game integration goes through SDK self-rendering.

### Channel management

- **Temporary channels** (landed 2026-10-15, carried by groups): event/dungeon temporary channels = groups with a TTL — `CreateGroupRequest.ttl_seconds` (field 7, 0 = permanent group; cap 30 days, over-limit/negative returns `INVALID_PARAM`), with the expiry moment converted into `GroupInfo.expires_at` (epoch milliseconds) delivered with `GET_GROUP_INFO` / `GET_USER_GROUPS` / `GROUP_CREATED_NOTIFY`, so clients can show a countdown and locally remove the group on expiry. **Expiry semantics**: the group is treated as nonexistent — member sends to the group channel return `AUTH_FAILED` (same semantics as non-members, zero send-gate changes), read paths remove it lazily (`GroupManager::LookupLocked` removes an expired group from the ledger and `user_to_groups_` on hit), and expired groups nobody touches are reclaimed periodically by `GroupExpirySweeper` (wired in the enhanced form, one sweep per 5 minutes; in basic, lazy removal already covers the semantics, sweeping is just memory reclamation). "Participants auto-join" is covered by the existing `CreateGroupRequest.initial_members`, zero additions. Inc 2 (the group-creation TTL parameter on the four SDK ends and client-side countdown rendering) landed 2026-10-15: C++ core `CreateGroup` gained a `ttl_seconds` overload (0 = permanent group, the two-parameter version unchanged); the TS dual packages carry it automatically via the schema (wire-lock tests add vectors); the web/desktop companion group-creation dialog gained validity presets (permanent / 1 hour / 1 day / 7 days), and group conversations show a "N min/hours/days left" countdown from `expiresAt` (15s clock granularity), with roster-driven pruning (leave/kick/expiry disappears locally, private chats not pruned).
- **Cross-server channels**: cross-server chat after a server merge. Routed by server_id.
- **Custom channels** (scope ruling 2026-10-15, carried by groups): players creating channels = creating groups — `CREATE_GROUP` (2101/2102) is a player-created named channel (group id is the channel id, in the GUILD channel domain), with the creator as OWNER able to grant ADMIN/MODERATOR (the `GroupMemberRole` ladder: kick/mute/alias and the rest of the management surface are all there). **Ruling**: no separate "custom channel" channel type will be built — the semantics fully overlap with the group system (trade channels / party channels are carried by group creation), and a separate channel namespace (cross-group search/directory/topic aggregation) waits for a real requirement in another batch.

### User behavior

- **Mute** (landed 2026-10-10, group-domain form): group MODERATOR+ mutes/unmutes members of the group (`SET_GROUP_MUTE_REQ/RESP` 2250/2251 + group-wide notify `GROUP_MEMBER_MUTED_NOTIFY` 2252; duration in seconds, 0=unmute, cap 30 days). While muted, that member's group-channel sends are rejected (`MUTED` return code, both basic/enhanced send gates intercept before storage, the message lands in no store); private chat / channels outside the ledger are unaffected. Mute state is delivered with `GroupMember.muted_until_ts` (`GET_GROUP_MEMBERS`), the GroupManager in-memory ledger expires lazily, sharing the group's own lifecycle. **Scope ruling**: the document's original "admin mutes all channels" needs a global admin identity, while chirp's chat-surface role system is group-scoped (no global identity to hang it on), so this batch lands group-domain muting; global muting comes with a global admin identity in another batch. All four SDK ends aligned (C++ core / sdks/ts / apps/shared/protocol / C#, 2250 round-trip + 2252 notify hook, 2026-10-10).
- **Reporting** (landed 2026-10-13, report-surface form): players report messages, `REPORT_MESSAGE_REQ/RESP` 2253/2254. The server's in-process in-memory ledger (`ReportLedger`) dedupes idempotently by (message_id, reporter_id) — a player repeatedly reporting the same message is not counted twice, and the response echoes the deduped cumulative `report_count`; the reported message must be in this instance's edit ledger (i.e. a message this instance actually delivered), otherwise `USER_NOT_FOUND` — the same semantics as recall's "message outside the ledger", which also blocks garbage message_ids from inflating the ledger's memory. The reason is optional, capped at 500 code points (server-validated), with at most 100 retained traces per message. **Scope ruling**: the document's original "admin dashboard moderation queue (dismiss/warn/mute/ban)" needs a global admin identity and a dashboard surface — the same ruling as group-domain muting: the moderation queue waits for the global admin surface in another batch; the time-retained ledger is its reserved consumption surface. All four SDK ends aligned (C++ core `ChatClient::ReportMessage`, the sdks/ts and apps/shared/protocol dual packages' `reportMessage`, C# `ReportMessageAsync`, 2253 round-trip + not-connected early exit, 2026-10-13); web/desktop message bubbles carry a report entry (Flag button + confirm; your own messages cannot be reported).
- **Chat level threshold** (ruled 2026-10-11, form ① adopted and landed): the world channel requires a declared level of at least `--world_channel_min_level` to speak, below it returns `LEVEL_REQUIRED = 13` (a new dedicated code). **Ruling basis and conclusion**: the whole chat chain has no player level data source (no level field in the login protocol, the account surface, or storage), with three candidate forms — ① **adopted**: `LoginRequest.level = 5` (client-declared, with the same trust level as the existing bare-userId login — the chat surface already trusts the login-declared identity itself, so adding a forgeable level changes nothing about the threat model and is the smallest change); ② a gateway bridge with a real data source is noted as a later enhancement (start it when real-time accuracy is needed); ③ an admin-dashboard allowlist was rejected (it would need a chat configuration API and dashboard surface first, out of proportion to the feature). **Landed form**: the declared level travels with the `SessionRegistry` session metadata (`session_to_level`, not identity metadata, read only by the world gate); the threshold flag defaults to **0 = off** (app/companion deployments see nothing, game deployments enable it explicitly, recommended 10); the gate sits in the auth/param tier of the send-gate chain (after parameter validation, before rate/pacing/repeat-mute/word-filter) — a failing send consumes no budget or filter work, and the AUTH_FAILED path for unauthenticated sessions is unaffected; wired identically in both basic/enhanced forms (enhanced inside the `on_send_message` gate chain). Tests: driven by basic production dispatch (default off / threshold reject / pass over the wall / private chat unaffected) + registry round-trip; the enhanced gate chain and free function are separate, and the test fixture cannot drive the threshold, so basic covers the semantics per the mute-batch precedent. All four SDK ends align the `level` declaration with login: C++ core `ChatClient::Login` trailing parameter (io-thread member archive, reused on renewal re-login), the sdks/ts and apps/shared/protocol dual packages' `ChatPipelineDeps.level?` getter (re-read each login round, default 0), C# `LoginAsync` trailing parameter (reused on renewal re-login); web/desktop `ChatApi.login` trailing parameter (the companion surface stays at default 0).
- **VIP privileges**: VIP player messages with colors, horn effects, exclusive emoji.

### Message display

- **Coordinate links** (landed 2026-10-13, message-display form): `msg_type = COORD_LINK = 15`, the coordinate payload rides `ChatMessage.metadata` (`CoordMetadata{map_id, x, y, z, label}`). The send side validates `ValidateCoordMetadata`: garbage metadata / missing `map_id` returns `INVALID_PARAM` (same tier as body-length validation, wired identically in both basic/enhanced forms, intercepted before any storage); metadata of non-COORD_LINK messages passes through verbatim (the protocol layer does not over-validate disabled message types). The storage chain is fully open: basic in-memory/Redis stores `ChatMessage` directly, enhanced goes through `MessageData` (offline queue + history) and the MySQL cold-tier BLOB column (HEX/UNHEX binary-safe, idempotent ALTER, tolerant of old databases without the column). All four SDK ends' sendMessage carries metadata: C++ core `SendOptions{msg_type, metadata}` (the local archive written too), the sdks/ts and apps/shared/protocol dual packages' `SendOptions.metadata` (both wire and local archive), C# `SendOptions.Metadata`. **Scope ruling**: the document's original "clickable auto-pathfinding to the coordinate" needs the in-game client's pathfinding surface, which the companion surface (web/desktop) lacks — it lands as a coordinate card (click to copy "x, y[, z]", zero-height omitted), with in-game integration via SDK self-rendering.
- **Achievement sharing** (landed 2026-10-14, companion form): `msg_type = ACHIEVEMENT`, card-style display (icon + name + rarity + description; the acquisition time is carried by the bubble's existing time label). The server validates metadata at the send gate — unparseable `AchievementMetadata` or a missing `achievement_id` returns INVALID_PARAM (same layer and posture as coordinate/item links, metadata of non-ACHIEVEMENT passes through verbatim; wired in both basic/enhanced forms); web `MessageBubble` and desktop `ChatPanel` render the achievement card (name colored by rarity, rarity text, description, achievement_id caption, iconUrl icon, `data-rarity` tag for test assertions); rarity is integer-coded 0-4 (common/fine/rare/epic/legendary, same color ladder as quality), with unknown values outside the enum falling back to common rendering. The in-game client's own achievement card rendering goes through the SDK side (same batch shape as item links: `AchievementMetadata` rides the generic ChatMessage.metadata pipeline, zero SDK changes across the four ends).
- **Guild recruitment** (landed 2026-10-15, companion form): `msg_type = GUILD_RECRUIT = 16`, card-style display (guild name + `Level N · Members M[/K]` + recruit text + guild_id caption). The payload rides `GuildRecruitMetadata{guild_id, guild_name, level, member_count, max_members, description}` (the generic metadata pipeline, zero SDK changes across the four ends); the server send gate validates — unparseable or missing `guild_id` returns INVALID_PARAM (same layer and posture as trade/achievement links, wired in both basic/enhanced forms); web `MessageBubble` and desktop `ChatPanel` render the guild card (max_members=0 shows only M). **Scope ruling**: the document's original "one-click join button" needs the guild system and a join-protocol surface (the companion surface has no such action surface) — it lands as a display card, with in-game integration via SDK self-rendering.
- **Party recruitment** (landed 2026-10-15, companion form): `msg_type = PARTY_RECRUIT = 17`, card-style display (dungeon name + `N needed · M/K` + leader + party_id caption). The payload rides `PartyRecruitMetadata{party_id, dungeon_name, needed, current, leader_name}`; the server send gate validates — unparseable or missing `party_id` returns INVALID_PARAM (same as above); web/desktop render the party card (current=0 shows only the N-needed). **Scope ruling**: the "one-click apply button" likewise — a display card, in-game self-rendering via the SDK.
- **Message search** (landed 2026-10-08/10-10): `SEARCH_MESSAGE_REQ/RESP = 2248/2249` (gateway.proto:158). The server-side chirp_search (TCP 5007) maintains a persistent SQLite FTS5 index (MySQL cross-check self-healing, fail-closed without downgrade; decision record docs/design-notes/message_search.md): CJK single-character tokens + Latin word-boundary tokenization, consistent on both sides, for FTS5 phrase matching, `channel_id`/`content_types` filtering, `(before_timestamp, before_message_id)` composite-cursor pagination (limit clamped to [1,50], default 20), with original-text highlight returned by the client (the server returns no snippet). Desktop `ChatApi.searchMessages` (226d912) + web `SearchDialog` (7e7a190, 5 unit tests); apps/shared/protocol `chat_pipeline.searchMessages` (wire round-trip + connection/keyword validation-order tests). **Divergence from this document**: the original "filter by keyword, time range, channel" — channel filtering landed (channel_id), the time range has no separate range parameter (before_* is a sort/pagination cursor, not an interval filter); message-type filtering is additionally supported.

### Game-specific

- **NPC dialog** (landed 2026-09-13): `services/game/npc_dialog` — the `NpcEngine` keyword rule table (ASCII case-insensitive substring matching, `*` fallback reply) + the `npc_responder` reply surface + the chat upstream link (`chat_npc_uplink`); `--metrics_port` instrumentation (event/reply counters). The interface is the seam for swapping in a smarter engine (e.g. an LLM service).
- **System broadcasts** (landed 2026-10-15, inject display-metadata form): the game plane's `MessageInjectRequest` (proto/game_server_gateway.proto) carries `priority`/`ttl_seconds` display fields (value range aligned with chat.Priority, default 0 with zero awareness); the chat side's `InjectConsumer` passes them straight into `ChatMessage.priority`/`ttl_seconds`, with zero server_gateway changes (whole-message forwarding). The marquee's two-element decision (URGENT + ttl>0, client `systemSurfaceOf`, independent of channel) and the system popup (HIGH) light up via injection; the rendering surface (marquee/popup/bubble coloring) landed 2026-10-14. **Scope boundary**: event sources (BOSS spawns / first kills / rare drops / player achievements) are on the game side; the inject's legal channel domain is PRIVATE..WORLD (validated by `InjectConsumer`), so injecting into the WORLD channel suffices.
- **Trade messages** (landed 2026-10-15, protocol + consumption form): `msg_type = TRADE_STATUS`, card-style display (status badge + item summary ×N + amount + trade_id caption). The server validates metadata at the send gate — unparseable `TradeMetadata` or a missing `trade_id` returns INVALID_PARAM (same layer and posture as coordinate/item/achievement links, wired in both basic/enhanced forms); `status` is display text not locked to the enum (the proto convention is CREATED/ACCEPTED/COMPLETED/CANCELLED, unknown values render as-is, and new status values are not blocked by old servers); web `MessageBubble` and desktop `ChatPanel` render the trade card (`data-trade-status` tag for test assertions). Zero SDK changes across the four ends (carried by the generic metadata pipeline). **Scope boundary**: the document's original "listing/bid/sold/expired status changes via the system channel" has its event source in the game-side auction house; the game plane's inject surface (`MessageInjectRequest`) currently has only content with no msg_type/metadata fields, so injecting card messages needs the inject protocol extended first (metadata passthrough) — a later enhancement; the player/SDK-side consumption chain (send gate + storage + rendering) is ready in this batch.
- **Friend online notification**: push notification when a friend comes online (disableable). ✅ Server landed (3025-3029, 2026-10-13): `SET/GET_NOTIFY_PREFS` user-level toggles (all on by default, Redis-persisted) + `FRIEND_ONLINE_NOTIFY` sent only on a transition of the effective state OFFLINE→non-OFFLINE (the login/SET_PRESENCE/game-assertion chains, filtered per recipient), body reusing `PresenceNotify`, roster 3021 unaffected. **Consumption side landed (2026-10-13/15)**: the TS dual packages' `msg_map` preference specs synced in both copies (the server returns INVALID_PARAM for a missing submessage, not silently treating it as "off"); web `social_api` (`onFriendOnlineNotify` subscribing to 3029, deduping self and off-roster users, ignoring malformed bodies) + desktop likewise; both ends' `ChatPage`/`MainWindow` show a single-slot toast, with the 3025/3027 toggles on the same surface.
- **Mail notification**: push notification when new mail arrives.

## P2 — Operations (long-term maintenance)

### Security and compliance

- **Anti-advertising** (the auto-mute part landed 2026-09-22, repeat-detection form): `RepeatGuard` (services/shared/chat/src/repeat_guard.h) tracks consecutive identical content per user — the 3rd identical consecutive send (`kRepeatTriggerCount`) opens a 5-minute mute window (`kRepeatMuteMs`), during which **all** content is rejected (not just repeated content), returning `RATE_LIMITED` (P0 duplicate detection and send-rate share this code); the gate sits after pacing and before word filtering, wired identically in both basic/enhanced forms (io-thread state, lock-free). **Scope ruling**: the document's original "flag for review" needs an admin dashboard moderation queue (a global admin surface) — the same ruling as report/mute, the moderation queue is another batch; the report ledger (ReportLedger, 2026-10-13) retaining by time is its reserved consumption surface.
- **Message audit**: all messages retained for N days (configurable). Retrievable from the admin dashboard.
- **Real-name linkage**: messages traceable to a real-name account. In support of report/complaint handling.
- **Anti-harassment** (landed 2026-10-15, recipient private-chat restriction form): `SET/GET_DM_RESTRICTION 2255-2258` recipient switch (default **off**, io-thread in-memory state — same lifecycle as the blocklist/channel mute, reset on process restart); once on, strangers' private messages are rejected with `DM_RESTRICTED` (common dedicated code 14, the message **lands in no store**: the gate is before the write). "Stranger" = not a social-plane friend **and** no shared group: the friend half is `FriendGraph` (services/shared/chat/src/friend_graph.cc) read-only consuming the snapshot the social service leaves in shared Redis at `chirp:social:friends:<receiver>` (`StoredFriendList`, key contract fixed with social's `main.cc`, no cache, fetched fresh each time), and the shared-group half goes through `GroupManager::ShareAnyGroup` (expired temporary groups participate per the lazy-removal semantics). Exemptions: friends, shared groups, the user's own session, NPC recipients. **Degradation direction = tighten**: missing Redis / missing key / corrupted snapshot are all treated as non-friend (the restriction keeps only the shared-group half in effect), no throw, no crash. **Scope ruling and divergence from the document**: the original "same guild" — the chat surface's group system is the GroupManager ledger (no separate guild plane), so "shared group" is its counterpart; the blocklist has stronger semantics (delivery-side silent drop, positioned after storage) and stacks with this switch — the two are not mutually exclusive. Wired identically in both basic/enhanced forms; the distributed form is not wired (same posture as the mute batch — no client toggle surface). **Client side landed** (2026-10-15): convenience APIs on all four SDK ends (C++ `SetDmRestriction`/`FetchDmRestriction`, the TS dual packages' `setDmRestriction`/`getDmRestriction`, C# `SetDmRestrictionAsync`/`GetDmRestrictionAsync`); the web settings surface = the friends panel's "stranger private-chat restriction" toggle (`dm-restriction-switch`, pulls 2257 on open, fires 2255 on toggle, silent failure re-pulled next open), desktop = the top bar's "private-chat restriction" button (same pull/toggle contract, greyed when unavailable); both ends give rejected bubbles a dedicated notice (`failureReason: 'dm_restricted'`, with "only friends/shared-group can message" wording).

### Performance and operations

- **Message persistence** (landed, the 2026-10-11/12 hybrid store form): `HybridMessageStore` (services/shared/chat/src/hybrid_message_store.h) dual-writes a Redis hot tier + a MySQL cold tier; when Redis is unavailable, messages land in an in-memory pending queue and are back-filled on recovery. History queries go hot-tier first, cold-tier fallback; recall tombstones hot-tier in-place rewrite + cold-tier flag-set; private quote targets scan the Redis synchronously-written hot tier first. MySQL goes through a connection pool (HEX/UNHEX binary-safe, idempotent ALTER tolerant of old databases without the column).
- **Message expiry** (landed 2026-10-15, enhanced-form retention window): the dual flags `--history_retention_days` (ordinary channels) and `--private_history_retention_days` (private chat, following the ordinary window when unset — "keep private chat longer" = the knob of configuring it larger), counted in days, **default 0 = off** (zero I/O for app/companion deployments). `HistoryRetentionSweeper` runs hourly (the timer arm in the same strand shape as MessageMigrationWorker), converting `now - retention` into a cutoff handed to `HybridMessageStore::ExpireBefore`: the hot tier (Redis history list) parses blob by blob and LRems item by item using each channel_type's own cutoff (blobs that fail to parse are left alone); the cold tier (MySQL archive) runs one DELETE for both cutoffs (epoch milliseconds are always positive, so a `cutoff <= 0` clause naturally matches no rows). Cleanup is best-effort (Redis/MySQL unavailable counts as 0, no throw). **Scope ruling**: the basic form (in-memory/Redis direct store) is not wired — in-memory state dies with the process, and its Redis list is a dev-smoke surface; the offline queue has its own TTL (`redis_offline_ttl_seconds`) outside the retention window.
- **Message compression** (server landed 2026-10-15, history read-back form): scope ruling — "bulk message transport" lands as **history read-back** (the large GET_HISTORY_RESP list direction; live fan-out/offline redelivery stay single-message, already small packets). Protocol (additive, invisible to clients that do not declare it): `LoginRequest.supports_gzip = 6` declared once at login (following the `supports_message_ack` client-capability precedent, session-level accounting, cleared on disconnect); successful history responses for declaring sessions carry `GetHistoryResponse.messages_gzip = 4` (bytes, gzip container RFC 1952) in place of plaintext `messages` — `code`/`has_more` stay in the outer layer, and the compressed payload is a **same-shape GetHistoryResponse carrying only the messages list**; the client decompresses and parses `.messages` back per the same type, with no side format on the wire. Empty lists are not compressed (plaintext empty list kept); on compression failure it falls back to plaintext rather than losing the message. The gzip container (windowBits 15+16) lets all four ends' runtimes read it with zero configuration (TS `DecompressionStream('gzip')`, C# `GZipStream`, Go `compress/gzip`, Java `GZIPInputStream`; on the C++ side zlib windowBits 15+32 auto-detect). `libs/common/gzip.{h,cc}` is the compression primitive (decompression carries a 16 MiB bomb cap), wired identically in all three server forms (basic/enhanced capability accounting via the SessionRegistry `gzip_sessions`, distributed via a local set; a re-login overwrites the declaration in both directions). **The decompression side has landed for the C++ core, the TS dual packages, C# and Android Kotlin (2026-10-15)** — `sdks/core` declares `supports_gzip` at login, `FetchHistory` reuses `chirp::common::GzipDecompress` to unwrap the same-shape payload and moves the list back into plaintext `messages`, reporting the existing `BadResponse` on a bad container/payload and the existing `Timeout` on timeout; the TS dual packages (`sdks/ts` + `apps/shared/protocol`) declare at login + `GET_HISTORY` decoding goes through the optional `inflateResponse` hook to unwrap (`DecompressionStream('gzip')`, zero dependencies across runtimes, 16 MiB decompression cap at the same value as C++), throwing `GzipError` on container corruption/over-limit so the layer above sees the failure and history is not silently dropped; `web_companion` / `desktop` already declare the capability at login. C# (`sdks/unity`) declares at login + the `GET_HISTORY` spec hooks the unwrap (`GZipStream` reads RFC 1952 with zero configuration, 16 MiB cap at the same value; **plus its own CRC/ISIZE trailer self-check** — `GZipStream` only validates the trailer when the final deflate block arrives, so a container truncated mid-stream would be silently read as a short list; the trailer self-check brings truncation back to an error consistent with C++/TS), throwing `GzipInflateError` on a bad container. Android Kotlin (`apps/android` protocol core) declares at login + `MsgSpecs.getHistory` hooks the unwrap (`GZIPInputStream` reads with zero configuration and carries its own trailer check, 16 MiB cap at the same value), throwing `GzipError` on a bad container. `sdks/unreal` is a thin facade over `sdks/core` and inherits the decompression surface automatically from the C++ core. iOS Swift / HarmonyOS decompression sides await landing (**blocker**: neither Foundation platform provides gzip container decoding — `NSData.decompressed(using: .zlib)` is a zlib container not RFC 1952, and the `Compression` framework only gives raw deflate — reading it would need a zlib `systemLibrary` target + FFI or a third-party package, while this repo has no runnable toolchain for either end, so written code could not be compile-verified; until it lands the capability is not declared, and the server always sends plaintext to undeclared sessions, leaving the plaintext path unaffected).
- **Multi-device sync** (landed, the multi-platform session form since 2026-09-14): the session registry keeps one slot per (user_id, platform) (libs/network/session_registry.h, same-pair rebinding kicks the old session — login replacement); delivery fan-out via `GetUserSessions` covers all online sessions of the account, so multiple devices receive live messages; read cursors broadcast to the relevant members via `MESSAGE_READ_NOTIFY` (multi-device read sync); the device list is seeded via `online_devices` + real-time add/remove via `DEVICES_PRESENCE_NOTIFY` (1020).
- **Message dedup** (landed, the 2026-09-18 companion form): web/desktop `message_store` drops duplicate appends by server message_id (live notify and SEND_MESSAGE_RESP confirm/history back-fill with the same id render only once); the C++ core normalizes the local archive by the same key. The server is stateless (naturally idempotent by (channel, message_id)).
- **Connection keep-alive** (landed, in batches on 2026-09-14/20): the C++ core's 25s heartbeat (pong echo verification + death on consecutive unanswered), 500ms→15s jittered exponential backoff reconnect, KICK as a terminal state with no reconnect (sdks/core/src/backoff.h); all four SDK ends share the shape (TS/C#/native). Message redelivery: the server's offline queue (hybrid store pending copies carry expires_at, redelivered at login, late-ACK cleanup `hybrid_message_store.cc:368`) + the client OfflineSendQueue (Swift/Kotlin native protocol cores, queueing and retrying sends while offline).

## Client rendering decision matrix

On receiving a message, the client decides the rendering mode along the three dimensions of `(channel_type, msg_type, priority)`:

```
priority check:
  priority == URGENT && ttl_seconds > 0 → top-of-screen marquee
  priority == HIGH && channel_type == SYSTEM → system popup

channel routing:
  channel_type → the corresponding tab/window (private tab, guild tab, world tab, ...)

message rendering:
  msg_type == TEXT → text bubble
  msg_type == ITEM_LINK → clickable item card
  msg_type == SKILL_LINK → clickable skill card
  msg_type == ACHIEVEMENT → achievement-share card
  msg_type == NPC_DIALOG → NPC dialog bubble (green)
  msg_type == TRADE_STATUS → trade-status card (orange)
  msg_type == SYSTEM → system message (yellow, centered)
```
