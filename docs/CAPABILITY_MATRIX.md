# Chirp Capability Matrix

Last verified: 2026-10-13

> Binary naming convention: `chirp_<plane>_<service>`. Game plane: `chirp_game_sdk_gateway`, `chirp_game_server_gateway`, `chirp_npc_dialog`; App plane: `chirp_app_sdk_gateway`, `chirp_app_auth`, `chirp_app_notification`; the search service is `chirp_search` (TCP 5007, reached by both planes' SDK gateways via `--search_host`); the shared chat binary is `chirp_chat` / `chirp_chat_distributed`, produced from one codebase under `services/shared/chat/`, with the deployment role (hub/spoke) selected by startup arguments.

This document describes the repository's current implementation state by runtime target, not by roadmap vision.

## Status legend

- `Supported`: part of the default documented backend trunk, must stay buildable
- `Experimental`: partially implemented, or behind an alternative target / specific environment dependency
- `Demo`: mainly for demonstration or local exploration, not a reliable backend contract
- `Stub`: placeholder, mock-driven, or clearly unfinished

## Backend services

| Game edge login / session routing | `chirp_game_sdk_gateway` (`services/game/sdk_gateway/`) | Supported | TCP 5000 / WS 5001, the game client edge: the main entry point for login, heartbeat and the kick flow; cross-instance kicks are scoped by platform (same user + same platform replaces, different platforms coexist, see the "multi-device online" row). With `--chat_host` set, it forwards chat business packets (2xxx) to chat over one per-client internal connection (SERVER_AUTH_REQ trust gate + login replay, relayed verbatim in both directions; if the pipe drops, the client is kicked so it reconnects); with `--search_host` set (default port 5007), 2248 search packets go through a second `ServiceBridge` instance over a degrade-semantics pipe to `chirp_search` (on a broken pipe it returns `SERVER_UNAVAILABLE` without kicking, and the next query redials automatically) |
| App plane auth basic token flow | `chirp_app_auth` (`services/app/auth/`) | Supported | The default binary is usable; without MySQL/libsodium it falls back to a simpler token verification path. the reported message must be in this instance's edit ledger, otherwise `USER_NOT_FOUND` is returned; the reason is optional up to 500 code points; the moderation queue awaits a separate batch for a global admin surface), anti-harassment private-chat restriction (`SET/GET_DM_RESTRICTION` 2255-2258, the recipient's switch defaults off; once on, private messages from strangers (not a social-plane friend snapshot and with no shared group) are rejected with the dedicated code `DM_RESTRICTED` (`ErrorCode = 14`) and the message lands in no storage at all; friends / same-group members / self / NPC are exempt; when Redis is missing or the snapshot is corrupt it tightens to non-friend — the restriction then only takes effect on the same-group half; the switch is io-thread in-memory state that resets with the process; SDKs: C++ core `SetDmRestriction`/`FetchDmRestriction`, both TS packages `setDmRestriction`/`getDmRestriction`, C# `SetDmRestrictionAsync`/`GetDmRestrictionAsync`), world-channel level gate (`--world_channel_min_level` defaults to 0 = off; the client-declared `LoginRequest.level` below the gate is rejected with the dedicated code `LEVEL_REQUIRED` (`ErrorCode = 13`)), history retention window (`--history_retention_days`/`--private_history_retention_days` in days, default 0 = off; if the private window is unset it follows the general window; the enhanced build's `HistoryRetentionSweeper` sweeps hourly — the Redis history list is LRem'd blob by blob using each channel type's own cutoff + one DELETE against the MySQL archive with both cutoffs, 2026-10-15), history read-back compression (`LoginRequest.supports_gzip=6` declared at login; sessions that declare it receive `GetHistoryResponse.messages_gzip=4` — a gzip container (RFC 1952) replacing the plaintext `messages`, whose payload is a same-shape response carrying only the messages list, so decompressing and parsing as the same type yields the list; empty lists are not compressed, and on failure it falls back to plaintext; sessions that did not declare it are always plaintext; the decompression side has landed for the C++ core, both TS packages, C# and Android Kotlin (`sdks/core` FetchHistory unwrapping; TS `GET_HISTORY` decode-side optional `inflateResponse` hook + `DecompressionStream('gzip')`; the `sdks/unity` spec unwrapping hook + `GZipStream` with its own CRC/ISIZE trailer self-check so a truncated container still errors; the `apps/android` protocol core spec unwrapping hook + `GZIPInputStream`), iOS has landed and is compile-verified in CI (PR #35 macOS runner: GzipTests 12/12, swift test 245/245; login already declares `supports_gzip`), and HarmonyOS code is written pending toolchain verification (shared-core injection seam + an `@ohos.zlib` decompressor, login does not declare it), 2026-10-15), coordinate links (`msg_type = COORD_LINK = 15`; the coordinate payload travels in the `metadata` field of `SendMessageRequest`/`ChatMessage` carrying `CoordMetadata{map_id, x, y, z, label}`; the send side's `ValidateCoordMetadata` tier check — garbage metadata / missing map_id returns `INVALID_PARAM`, rejected at the same layer as the body-length check, before storage, with both the basic and enhanced builds wired the same way, and non-COORD_LINK metadata is passed through verbatim; metadata round-trips through history read-back, the offline queue and the MySQL cold-tier BLOB column (HEX/UNHEX binary-safe) along the whole chain), and direct-entry rate limiting (fixed windows for per-IP login / per-user send, Redis-backed, fail-open; the enhanced build's limiter gate is off by default, enabled explicitly with `--login_rate_limit_per_min`/`--send_rate_limit_per_min`) are all wired into the default binary. The direct client entry points (7000/7001) stay open during the edge transition period; with `--gateway_service_secret` set, connections that pass the SERVER_AUTH_REQ trust gate (gateway pipes) skip the per-IP login rate limit; with `--token_secret` set, login requires an HS256 JWT whose secret aligns with auth's `--jwt_secret` |
| Multi-device online (same-type replacement + online device list) | `libs/network` (`session_registry` + `device_presence`, wired into both sdk_gateways and chat/party/social) | Supported | Since 2026-09-27 the session slot key is **(user_id, platform)**: a new login on the same platform replaces the old session (KICK_NOTIFY reason `"logged in on another <platform>"`, legacy empty platform falls back to the "device" wording), and different platforms coexist without interfering; a reconnect with the same device_id rebinds idempotently (same device_id necessarily means same platform); device_id is demoted to per-session metadata. An empty platform normalizes to "default", and legacy clients that do not report a platform keep the old one-session-per-user behavior. **Web multi-tab same-type mutual replacement is a direct consequence of this semantics, and no special case is opened for it** (browsers have no stable device identity). The login response carries an initial `online_devices` list (`LoginResponse.online_devices`, excluding the session itself); login/disconnect/replacement broadcast `DEVICES_PRESENCE_NOTIFY` (1020, sequence 0, payload `[{platform, device_id, online, ts}]`) to the user's other online sessions; the disconnect broadcast is only sent when the slot release is confirmed — a late disconnect from a replaced old session does not produce a false offline. The broadcast is registry-local: in a multi-node deployment other instances do not hear it, the same boundary as the existing local notify. The Redis cross-instance claim also migrates to the platform key (`chirp:sess:<user>\x1F<platform>`); the voice plane is deliberately untouched (it is designed as one session per user); party/social only switch the replacement key and do not broadcast the device list (the device list belongs to the client access plane). Three SDK layers can receive it: Go `SetDevicePresenceHandler`, TS `@chirp/protocol` (`onDevicesPresence`/`onLoginDevices`), and the native Android/iOS `ChatEventListener` with the same two hooks; web (a sidebar Dialog with an online count) has minimal UI, and the Flutter mobile client used to carry the list on its "Profile" page (removed on 2026-09-29 with the native migration). Tests: `session_registry_tests` rewritten with 25 cases, `chat_enhanced_session_tests` for cross-type coexistence/online-offline announce, the party/social/app/game gateway suites updated in sync, Go dispatch, and web store+components, mobile store+api+widget |

## Recommended external framing

When introducing this repository externally, the appropriate current description is:

- One supported core backend trunk: `gateway + auth + chat`
- A proving ground: distributed chat, more complete authentication, voice, social and multi-engine SDKs are all being tried here
- Treat the mobile/admin ends as demo repos, not finished suites
